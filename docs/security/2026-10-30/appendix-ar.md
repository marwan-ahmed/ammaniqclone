## إعدادات وفجوات ضمان منفصلة عن الثغرات المثبتة

### CFG-01 — تعطيل تحقق شهادة PostgreSQL في إعداد الأساس — مشروط، عالية إن كان فعالاً

[db/index.ts:11](D:/ajeeb-company/ahmed-eyad/app/src/db/index.ts:11) يضع `rejectUnauthorized:false`، ما يسمح بقبول شهادة غير موثوقة إذا كان هذا إعداد الاتصال الفعال، مع خطر اعتراض الاتصال. **لا نجزم أنه فعال في الإنتاج**: [توثيق pg](https://node-postgres.com/features/ssl) يوضح أن خيارات SSL في connectionString تستبدل كائن ssl، و.env.example يحتوي sslmode=require. لم نقرأ قيمة DATABASE_URL الفعلية.

اختبار محلي بتهيئة Client دون connect وبروابط اصطناعية أثبت: دون sslmode يبقى rejectUnauthorized=false، ومع require أو verify-full في النسخ المثبتة يصبح ssl كائناً افتراضياً متحققاً. pg يحذر أن دلالة require ستتغير في إصدار رئيسي لاحق. الإصلاح: ضبط تحقق هوية الخادم صراحةً، والتحقق من الإعداد الفعال دون تسجيل الرابط؛ القبول اختبار شهادة خاطئة/اسم مضيف مخالف على بيئة تجريبية يجب أن يفشل.

### CFG-02 — لا سياسة headers أمنية مخصصة ظاهرة في المستودع — فجوة ضمان

[next.config.ts:3](D:/ajeeb-company/ahmed-eyad/app/next.config.ts:3) يضبط allowedDevOrigins فقط؛ [vercel.json](D:/ajeeb-company/ahmed-eyad/app/vercel.json) لا يضيف CSP أو frame-ancestors أو سياسة headers مماثلة. لا نفترض غياب HSTS أو headers التي قد تضيفها المنصة. غياب CSP لا يثبت XSS وحده، لكنه يقلل الدفاع أمام SEC-07؛ غياب سياسة framing قد يتيح clickjacking إذا لم تضفها المنصة.

القبول: قراءة headers الفعلية للنشر ومراجعة CSP ملائمة لـFirebase والطباعة والخطوط، ومنع framing غير المصرح. layout.tsx:25 يحتوي script ثابتاً داخل HTML؛ تفعيل CSP صارم يحتاج nonce/hash صحيحاً، دون كسر التطبيق أو إضافة unsafe-inline بصورة عمياء.

### OPS-05 — المال في JavaScript والضمانات على قاعدة البيانات

المبالغ مخزنة في PostgreSQL بنوع numeric(18,2)، وهو ضبط إيجابي. لكن API يحولها إلى JavaScript Number ويستعمل parseFloat وMath.round وtoFixed؛ حدود الدقة والأحجام ومجموع الحصص تحتاج invariants صريحة. لا نعد استعمال Number وحده خسارة مالية مثبتة لكل عملية؛ حالات الفشل المثبتة مذكورة في SEC-12 إلى SEC-17.

TypeScript ليس حاجز تحقق وقت التشغيل، وReact لا يهرب القيم التي تُجمع يدوياً في document.write أو ملفات CSV. لا دليل على ثغرة جديدة في «لغة TypeScript» ذاتها؛ النتائج تخص استعمال اللغة وDOM وحدود الثقة وإصدارات المكتبات. schema يتضمن أطوالاً وforeign keys وunique، لكنه لا يعرّف CHECKs لحماية حدود المال أو مجموع النسب، ولا uniqueness لمحفظة الشركة أو مفتاح سداد مانع للتكرار.

## ما يحتاج تحققاً من بيئة الإنتاج

| المجال | ما لم يثبت من الملفات | دليل الإغلاق المطلوب |
| --- | --- | --- |
| إتاحة النشر | حماية Vercel/WAF/preview والنطاق العام | اختبار وصول مسموح ومرفوض من شبكات مناسبة، بعد تجهيز بيئة آمنة |
| قاعدة البيانات | صلاحيات المستخدم، RLS، الشبكة، التشفير والنسخ | حساب تطبيق بأقل الصلاحيات، إعداد TLS فعال، تجربة استعادة وRPO/RTO موثقان |
| Firebase | MFA للمديرين، سياسة كلمات المرور، email enumeration protection، النطاقات والجلسات | مراجعة لوحة وإجراءات إلغاء الجلسات/تعطيل الموظفين واختبارات قبولها |
| الأسرار | حقوق الوصول للبيئة وتاريخ التدوير وفصل preview/production | مراجعة بدون عرض القيم، إثبات عزل البيئات وإلغاء أسرار متعرضة إن ثبت تعرضها |
| الاستجابة للحوادث | سجلات وصول وتغييرات وتنبيهات واحتفاظ | ربط معرف الطلب بالمستخدم والعملية، وتنبيه تغييرات الأدوار/reset والعمليات غير المعتادة |
| الاستضافة والبناء | Node الفعلي وLinux/glibc ومعالجة الصور وheaders | جرد runtime والاعتماديات المبنية وإعادة مطابقة النشرات مع الإعداد الفعلي |

لا دليل كافياً على CSRF مستقل يتجاوز جلسة لأن API لا يتطلب جلسة أصلاً؛ غياب التوثيق هو المشكلة الأسبق. عند إضافة cookies يلزم تصميم حماية CSRF ملائم. CORS ليس تفويضاً، ولا يمنع عميلاً مباشراً من استدعاء API.

لم نجد upload endpoint أو استعمال user input في shell/eval أو SQL خام مركب من المدخلات في المسارات المراجعة. innerHTML المنسوخ من DOM أنشأه React وCSS الثابت في CollectorReportModal لا يثبتان XSS بمفردهما. لم يُجر تدقيق شبكي للمزودين أو اختبار اختراق حي، لذلك تظل البنود الخارجية أسئلة تحقق، لا ثغرات مؤكدة.
